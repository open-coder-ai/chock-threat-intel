## What changed

### GitSpawn — malicious `.git/config` triggers RCE in seven AI coding agents via `core.fsmonitor`

**Source:** [CSA Research Note — GitSpawn: How a Git Config File Hijacks AI Coding
Agents](https://labs.cloudsecurityalliance.org/research/csa-research-note-gitspawn-ai-coding-agent-rce-20260903-csa/)
(Cloud Security Alliance, Sep 3, 2026) and the follow-up [CSA Research Note — GitSpawn:
Malicious Git Configs Hijack AI Coding
Agents](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-agent-git-config-rce-20260904-cs/)
(Sep 4, 2026), both reporting Manifold Security's original disclosure · direct fetch of
labs.cloudsecurityalliance.org is proxy-blocked in this environment — corroborated via [The
Hacker News — Malicious Git Configs Can Make Claude, Codex, Cursor and Other AI Agents Run
Attacker
Code](https://thehackernews.com/2026/09/malicious-git-configs-can-make-claude.html),
[Cyber Security News — GitSpawn Flaws Let Malicious Repositories Execute Code in Claude Code,
Codex, Cursor, and Grok](https://cybersecuritynews.com/gitspawn-flaws-execute-code/), and
[GBHackers — GitSpawn Flaw Enables Arbitrary Code
Execution](https://gbhackers.com/gitspawn-flaw-enables-arbitrary-code-execution/), all
agreeing on the researcher, mechanism, vendor list, and dates

Manifold Security disclosed GitSpawn, a vulnerability class in which a repository's own
`.git/config` forces a command-line AI coding agent to execute attacker-chosen code the
moment the agent inspects the repository — no tool-call approval prompt, and in several
cases no user action of any kind. The mechanism abuses `core.fsmonitor`, a legitimate Git
performance setting naming a helper program Git runs automatically whenever an operation
refreshes the repository index. Because coding agents routinely run background `git status`
/ `git diff` calls to orient themselves on startup, they trigger the attacker's helper
program without the agent ever issuing an explicit "run this command" tool call — the
execution happens inside Git's own subprocess spawn, outside the agent's normal tool-call
path entirely. Exploitation requires the `.git` directory to arrive intact (shared archive,
synced folder, USB stick, or an unpacked zip) rather than via a plain `git clone`, which does
not carry over a attacker-planted local config the same way.

Manifold documented eight findings across seven agents: **Claude Code, OpenAI Codex, Cursor,
Block's Goose, Alibaba's Qwen Code, xAI's Grok Build, and Hermes Agent.** Patch status as of
the Sep 1, 2026 retest: fixed in Goose, Claude Code, and Cursor (Claude Code's `core.fsmonitor`
path patched in v2.1.196, Jun 26, 2026, per the corroborating reports); still exploitable in
Qwen Code, Grok Build, Hermes Agent, and a second variant in Claude Code. No CVE identified in
the corroborating coverage as of this writing.

**Catalog mapping:** Structurally distinct from Plugin4Shell (a supply-chain/plugin-pinning
break) — GitSpawn is a *repository-content* attack that reaches code execution through Git's
own internal subprocess spawn, not through anything the agent's tool-call layer mediates.
That places it on **MITRE ATLAS [AML.T0112 Machine Compromise (Local AI
Agent)](https://atlas.mitre.org/techniques/AML.T0112)** and **OWASP ASI05 Unexpected Code
Execution (RCE)** / **LLM03 Excessive Agency**, which this ledger already scores
`enforced (slice)` via `block-unsafe-code-execution` and `block-destructive-commands`. Both of
those guards are described in the catalog as pre-tool-use gates on commands the agent
explicitly issues. **This ledger cannot verify from this repository whether those guards also
intercept a subprocess Git spawns on its own initiative** (via a `.git/config`-named helper,
triggered by a routine `git status`/`git diff` the agent runs for context, before any
tool-call the guard would see) **or whether they see only the agent's own direct tool
invocations** — that check belongs in `chock-catalog`, not here, same posture as the
Plugin4Shell flag from last week. Status left unchanged (`enforced (slice)`) but flagged as a
second open verification item on the AML.T0112 coverage row.
