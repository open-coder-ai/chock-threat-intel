## What changed

### Microsoft: post-training supply-chain backdoors and a weight-space "sleeper agent" reach a coding agent's own tool calls

**Sources:** [Trained to betray: How post-training supply chain attacks hijack coding
agents](https://www.microsoft.com/en-us/security/blog/2026/11/12/trained-to-betray-how-post-training-supply-chain-attacks-hijack-coding-agents/)
(Microsoft Defender Research + Microsoft AI Red Team, Nov 12, 2026) and [Detecting sleeper
agents hiding in AI model
neurons](https://www.microsoft.com/en-us/security/blog/2026/11/10/detecting-sleeper-agents-hiding-in-ai-model-neurons/)
(Microsoft Research, Nov 10, 2026) — both fetched directly, no proxy block on microsoft.com.

**Trained to betray** describes two post-training attacks, both demonstrated as research, not
observed exploitation:

- **Dataset poisoning (Defender Research):** ~90 poisoned rows planted in a ~9,000-example
  fine-tuning set (via hub impersonation, namespace reuse, compromised accounts, or scraped
  planted content) pair an ordinary request with an unrelated, unsafe tool call (e.g., a
  `curl`-then-`source` fetch-and-run of a remote script). Fine-tuning `gpt-4.1-mini` on the
  poisoned set triggered the unsafe tool call in 78.0%/77.8% of 500 trials on the two training
  harnesses (11.0%/0% transfer to two unseen harnesses). One real-world public dataset was
  found to contain risky rows of this shape; no confirmed exploitation.
- **Model poisoning (AI Red Team):** SFT-then-RL implants a trigger into an open-weight
  checkpoint (`Qwen3.5-4B`/`9B` tested), distributed via a model hub with no knowledge of the
  victim's harness. Tested against Claude Code, Codex CLI, and "Pi" harnesses — Microsoft states
  the risk arises only when a harness is configured to run a backdoored checkpoint, not from
  default Claude Code or Codex CLI configurations. Attack success on unseen repositories reached
  84.1–94.8% in the strongest configuration.

**Detecting sleeper agents** is defensive/detection research (Microsoft states it has not
observed the technique used by threat actors), but documents the attack it defends against: an
attacker who can touch a model's weights edits fewer than 10 neurons to implant a trigger;
needs only inference-level compute (no training run); the model passes standard evals; on
seeing the trigger string in context, it issues an attacker-chosen command that "the agent runs
... with whatever access it has." Notably, Claude Code running Opus 4.5 is credited with
autonomously surfacing most of the underlying threat that human researchers then studied.

**Catalog mapping — the poisoning is out of scope, same as every training-time entry; the
*triggered tool call* is the new wrinkle.** The poisoning step (dataset or weights) is
training-time tampering — same declared-out-of-scope rationale as OWASP LLM05 Data & Model
Poisoning / DSGAI04 and MITRE ATLAS's training-pipeline techniques elsewhere in this ledger; a
repo-local guard cannot reach a model's training process. OWASP **ASI04 Agentic Supply Chain
Vulnerabilities** / **LLM04 Supply Chain** (tampered models) is the closest named risk for the
poisoning step itself — already `enforced (slice)`/`enforced (slice)` via
`block-unpinned-agent-components` for *pinned-artifact* supply chain, though that guard pins
installed plugins/components, not arbitrary fine-tuned or third-party model checkpoints a user
points a harness at; this ledger cannot confirm from this repository whether checkpoint
selection is a `chock.lock`-governed path at all. Left unscored on that specific question rather
than guessed at. The part this ledger *can* score: unlike GitSpawn (a subprocess Git spawns on
its own, outside any tool call) or Plugin4Shell (a checkout-time Git ref/commit ambiguity), both
Microsoft attacks' payloads surface as an ordinary, schema-valid **tool call** that a harness
executes through its normal tool-call path — the same path **AML.T0112 Machine Compromise (Local
AI Agent)**'s existing `enforced (slice)` coverage (`block-unsafe-code-execution`,
`block-destructive-commands`) already watches. Whether those guards' pattern-matching catches
the *specific* payload shapes demonstrated here (a `curl | source` fetch-and-run; an
attacker-chosen command on neuron-edit trigger) is the same "a floor, not a sandbox" limit
already declared on that row — field validation of an existing honest caveat, not a newly
discovered gap. No status change; no new row.

### ARTEX (Storm-3358) expands to the financial sector — same incident family as the Oct 7 CrowdStrike report

**Source:** [ARTEX abuse expands as cybercriminals target financial
sector](https://www.microsoft.com/en-us/security/blog/2026/11/06/artex-abuse-expands-as-cybercriminals-target-financial-sector/)
(Microsoft Threat Intelligence, Nov 6, 2026; fetched directly). In October 2026, **Storm-3358**
— a financially-motivated, Cambodia-based cluster targeting mostly Southeast Asian financial
organizations — began pairing **ARTEX** (an open-source "agentic AI offensive framework" that by
default scripts Nmap, curl, wget, Python HTTP clients, and headless Chromium/Playwright) with
conventional scanning to exploit anonymous-upload and SSRF flaws and deploy open-source RATs
(WISP, vshell, AdaptixC2). Not a new technique: this is the same ARTEX tooling, and the same
MITRE ATLAS autonomous-operation technique family (AML.T0116/T0117/T0124, already declared
**out of scope** for a repo-local guard — see [digests/2026-10-16.md](2026-10-16.md)), as the
CrowdStrike South Korean-banks report this ledger already tracks; this is that incident family
continuing and widening its target list, not a new entry. No status change.

### MITRE ATLAS v2026.10's three previously-unscored techniques, resolved

**Source:** [raw.githubusercontent.com/mitre-atlas/atlas-data .../dist/v6/ATLAS-2026.10.yaml](https://raw.githubusercontent.com/mitre-atlas/atlas-data/refs/heads/main/dist/v6/ATLAS-2026.10.yaml)
(fetched directly — github.com/githubusercontent.com is not proxy-blocked; atlas.mitre.org's
technique pages themselves remained DNS-blocked this week, same as every prior week). The Oct 30
digest left **AML.T0138 Indicator Removal**, **AML.T0142 Event Triggered Execution**, and
**AML.T0143 LLM Prompt Propagation** unscored because their technique pages were unreachable.
Their actual descriptions, read from ATLAS's machine-readable release data this week:

- **AML.T0138 Indicator Removal** (tactic: Defense Evasion) — "Deleting or altering logs,
  records, and artifacts to conceal activity, including by autonomous agents tampering with
  their own transcripts." This is a direct match for this ledger's own open **OWASP T8
  Repudiation & Untraceability** gap (roadmap item
  [chock#33](https://github.com/open-coder-ai/chock/issues/33), a tamper-evident gate log) — no
  catalog mechanism protects an agent's own action log/transcript from the agent's own tampering.
  **Added to the coverage table below as `policy wanted`**, tied to the same chock#33 roadmap
  item as T8.
- **AML.T0143 LLM Prompt Propagation** (tactic: Lateral Movement) — "Spreading malicious
  instructions already in an AI environment to other storage locations, agents, or resources."
  This is the generalized, numbered form of the prompt-worm concept this ledger's own ATLAS
  LLM-core list already names (**AML.T0061 Prompt Self-Replication**) but has never carried a
  coverage row for. No catalog mechanism inspects content being written to new files, memory, or
  other agents for self-propagating injected instructions. **Added to the coverage table below
  as `policy wanted`.**
- **AML.T0142 Event Triggered Execution** (tactic: Persistence) — "Establishing persistence by
  modifying hooks or handlers so adversary code runs when a system or application event occurs."
  For the slice of this that is an agent's own hook/handler configuration, this is the same
  mechanism class as the already-scored **AML.T0081 Modify Agent Configuration**
  (`protect-agent-config`‡, `enforced (slice)‡`) — resolved as adjacent, no new row. The
  technique's description is not limited to agent-specific hooks, though (cron, systemd units,
  shell rc files, and other OS-level event handlers a coding agent's shell commands could reach
  are the same kind of trigger); this ledger cannot confirm from this repository whether
  `protect-agent-config` reaches any such OS-level persistence path outside recognized agent
  config files. Left as a verification gap on the existing AML.T0081 row's prose rather than a
  new row or a guessed status.
