## What changed

### MCP Python SDK — six advisories: OAuth credential redirection, token-audience confusion, cross-origin credential leak, SSRF via schema `$ref`, two resource-exhaustion DoS bugs

**Source:** GitHub Security Advisories, `modelcontextprotocol/python-sdk`, published by
maintainer `maxisbey` Sep 28 – Oct 5, 2026 — all six fetched directly, no proxy block on
github.com:

- [GHSA-qx49-fqc8-xw99](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99)
  — "OAuth client could send credentials to an authorization server chosen by the MCP
  server" (Sep 28, High, CVSS 7.5, CWE-345/CWE-522, no CVE assigned)
- [GHSA-rwrf-2pqf-9j8j](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-rwrf-2pqf-9j8j)
  — "Client fetched server-chosen `$ref` URLs while validating tool results against output
  schemas" — SSRF (Sep 28, Moderate/7.5 for unattended agents, CWE-918, no CVE assigned)
- [GHSA-84m7-p3x7-pcfv](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-84m7-p3x7-pcfv)
  — "Streamable HTTP sessions were never reclaimed by default and kept their initialize
  payloads" — unbounded memory growth (Sep 30, High, CVSS 7.5, CVE-2026-59951, CWE-770/772)
- [GHSA-fmmv-w9g8-j3gc](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-fmmv-w9g8-j3gc)
  — "HTTP server transports and OAuth endpoints read request bodies with no size limit"
  (Sep 30, High, CVSS 7.5, CWE-770, no CVE assigned)
- [GHSA-5h93-6whr-6q8j](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-5h93-6whr-6q8j)
  — "HTTP client transports followed cross-origin redirects carrying custom headers and
  bodies" (Oct 2, Moderate, CVSS 5.9, CWE-200, no CVE assigned)
- [GHSA-w4fh-qvv9-3v23](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-w4fh-qvv9-3v23)
  — "Server bearer-token authentication accepts tokens issued for a different resource
  server" — audience-confusion (Oct 5, Moderate, CVSS 6.8, CWE-863, no CVE assigned)

All six are patched in `mcp` 1.30.0 / 2.2.0 (GHSA-fmmv-w9g8-j3gc patched earlier, in 1.29.1 /
2.1.0). Corroborated independently by [Cycode's research
write-up](https://cycode.com/blog/mcp-python-sdk-oauth-account-takeover/) (credited finder,
Yuval Elbar, for the OAuth advisory; direct fetch of cycode.com is proxy-blocked in this
environment) and a [Cloud Security Alliance research
note](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-python-sdk-oauth-flaw-20260930-csa-sty/)
dated Sep 30, 2026 (direct fetch of cloudsecurityalliance.org is proxy-blocked; CSA's note is
itself marked AI-assisted, unreviewed — treated as corroboration only, not as the primary
citation).

The two OAuth/credential bugs (GHSA-qx49, GHSA-5h93) let a connected or redirecting MCP
server exfiltrate a client's OAuth client secret, authorization code, PKCE verifier, or a
custom credential header — textbook **AML.T0098 Agent Tool Credential Harvesting** against
an MCP *client*. The audience-confusion bug (GHSA-w4fh) is a **privilege-escalation / identity
abuse** flaw (OWASP **ASI03**) on the *server* side: a token minted for one resource server is
accepted by another. The SSRF bug (GHSA-rwrf) matches Unit 42's scenario 4 (internal-network
SSRF via a tool call) and **AML.T0053 AI Agent Tool Invocation**. The two resource-exhaustion
bugs (GHSA-84m7, GHSA-fmmv) are **OWASP T4 Resource Overload / LLM06 Unbounded Consumption /
AML.T0034.002 Cost Harvesting: Agentic Resource Consumption**.

**Catalog mapping — field validation, no status change.** This ledger's own AML.T0110 row
already states the limit of `verify-mcp-allowlist`'s `enforced (slice)` coverage in its own
prose: "membership is checked, not what an allowed server's tools say or return." These six
advisories are exactly that — bugs in *what a connected server's implementation does* once a
client has already decided to talk to it, which an allowlist of server identities structurally
cannot reach. That is not a new open question to flag (unlike Plugin4Shell/GitSpawn above, which
asked an unanswered question about `chock-catalog` internals); it is confirmation that the
already-declared gap is real in the field. No row changes status. The resource-exhaustion pair
is field validation of the already-`policy wanted` LLM06/AML.T0034.002 gap — a budget/rate-limit
gate (needed for that gap to close) would be the mechanism kind that could eventually reach
*server-side* resource exhaustion too, but none exists today. **`verify-mcp-allowlist` is
unaffected by and does not need to change for this finding** — chock does not vendor or run the
MCP Python SDK itself; this is upstream-dependency exposure for any coding agent or MCP server
built on it, same declared-scope posture as Plugin4Shell and GitSpawn being bugs in *other*
vendors' agents, not chock's own mechanism.
